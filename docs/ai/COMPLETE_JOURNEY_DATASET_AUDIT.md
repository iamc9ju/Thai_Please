# Complete Journey — ผลตรวจไฟล์จริงสำหรับการแนะนำเควส

วันที่ตรวจ: 14 ตุลาคม 2026

**ข้อสรุป:** ชุดนี้เหมาะเป็นข้อมูลต้นทางสำหรับทดลอง AI แนะนำเควสจากพฤติกรรมซื้อ มีผู้ซื้อที่ซื้อซ้ำ สินค้า หมวด ร้านค้า และเลขตะกร้าครบกว่าชุด AmExpert ที่ตรวจไว้ก่อนหน้า งานปลายทางยังเป็นเควสได้ แต่ต้องออกแบบเป้าหมายการฝึกและ mapping ก่อนใช้ ไม่ใช่นำเข้า classifier เดิมที่ทำนายความสำเร็จเควสได้ทันที

รายงานนี้เป็นการตรวจข้อมูลสำหรับ `FR-C07`, `FR-S01–FR-S03` และขอบเขตการตรวจ completion ของ `FR-S06` ไม่เปลี่ยน requirements, schema, feature contract หรือโมเดล และไม่ถือว่า requirements เหล่านี้พัฒนาเสร็จแล้ว

## 4. ความหมายเวลาและการแปลงที่ผู้เผยแพร่ทำ

[Source preparation script ของ revision เดียวกัน](https://github.com/bradleyboehmke/completejourney/blob/5b5d06192b9856edd04e4d405787af2f2e4a1fef/data-raw/prep-data.R) แสดงว่า:

- เลือกช่วง 365 วันจาก source แล้วเปลี่ยนแกนวันที่ให้เริ่ม 2017-01-01 ดังนั้นปี 2017 ไม่ใช่หลักฐานว่าธุรกรรมต้นฉบับเกิดปีนั้นจริง
- ลบรายการหนึ่งในวัน Christmas ตามสมมติฐานผู้เผยแพร่ จึงพบ 364 วันตามเวลา New York
- สร้างวินาทีจากเลขตะกร้า ไม่ใช่วินาทีจริงที่สังเกตได้ และปรับบางชั่วโมงในวันเปลี่ยน DST
- สร้าง timestamp ด้วย timezone `America/New_York`; audit อ่านระบุ UTC ชัดเจน ไม่ใช้ timezone ของเครื่อง
- ช่วง UTC คือ `2017-01-01T11:53:26Z` ถึง `2018-01-01T04:01:20Z` ขอบท้ายที่เข้าสู่ปี 2018 เป็นผลจากการแปลง timezone

เหมาะกับการทดลองพฤติกรรมรายวัน/รายสัปดาห์ แต่ห้ามอ้างความแม่นยำของลำดับระดับวินาทีหรือปีปฏิทินต้นฉบับ ใช้ช่วงประวัติก่อน cutoff เป็น features และช่วงถัดไปเป็นผลซื้อที่ต้องการทำนาย แบ่ง evaluation ตามเวลา

ไม่พบ sales value หรือส่วนลดติดลบในไฟล์ที่เผยแพร่ แต่ preparation script เปลี่ยนส่วนลดเป็นค่าสัมบูรณ์ และเปลี่ยน retail discount บางค่าจากต้นฉบับเป็นศูนย์ จึงไม่ใช่ snapshot การเงินดิบที่ตรวจย้อนกลับได้ครบ

`sales_value` ถูกอธิบายใน [data dictionary](https://bradleyboehmke.github.io/completejourney/reference/transactions_sample.html) ว่าเป็นยอดที่ผู้ค้ารับจากการขาย ไม่ใช่ unit price ห้ามคูณ quantity ซ้ำ ห้ามหักส่วนลดทั้งหมดซ้ำโดยไม่ยืนยันว่ารวมส่วนลดและ coupon reimbursement อย่างไร และยังไม่ยืนยัน mapping เป็น `Order.finalAmount` ตามกฎเรา

ค่าต้นทางเป็น R double; audit ตรวจว่าใกล้ระดับ cents โดยส่วนต่างสูงสุดต่ำกว่า `0.00000001` cent แล้วแปลงด้วย Decimal เป็น integer cents เพื่อรวมยอด บันทึกส่วนต่างใน summary ไม่มีการใช้ floating-point รวมเงิน และไม่มีการแปลง dollars เป็น THB

พบหมวดที่อาจไม่ใช่สินค้าที่เราต้องการ เช่น FUEL, COUPON และ MISCELLANEOUS ต้องเลือกขอบเขตและตรวจผลต่อยอดทั้งตะกร้า หากยกเว้นบางรายการ ห้ามอ้างว่ายอดที่เหลือเท่ากับยอดใบเสร็จเดิม

## 7. ใช้กับงาน AI ให้เควสได้อย่างไร

| องค์ประกอบงานเรา                  | ความพร้อมจาก source                                                                                            |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| ความถี่ซื้อ 7/30 วัน              | มีเลขตะกร้าและ timestamp; คำนวณ distinct baskets หลังเลือกข้อมูลที่ใช้ได้                                      |
| ความสนใจสินค้า/หมวด               | มี product ID และ category/type; ต้องจัดการ missing และ mapping หมวดของระบบ                                    |
| พฤติกรรมต่อร้าน                   | มี store ID; ใช้เรียนรู้ความสัมพันธ์กับร้านต้นทางได้ แต่ต้องออกแบบการแทนร้านในระบบเรา                          |
| ยอดรวม/ยอดเฉลี่ยต่อการซื้อ        | รวม source sales value ต่อ basket ได้; ต้องยืนยันความหมายราคาและหน่วยก่อนเทียบกับยอดสุทธิในระบบ                |

| แต้ม เป้าหมาย และวันหมดอายุ       | เป็นนโยบายที่ระบบเรากำหนด ไม่ใช่ facts จาก dataset                                                             |
| ผลสำเร็จเควส/ประวัติเควส          | ไม่มี; ห้ามเติมให้เป็นประวัติเควสจริงหรืออ้างว่าโมเดลทำนายโอกาสสำเร็จเควสแล้ว                                  |
| Payment success / reward issuance | source ไม่มี payment status หรือ immutable receipts ตาม contract ของระบบเรา; backend ยังตรวจจากข้อมูลของเราเอง |

แนวทางที่เสนอให้พิจารณาหลัง audit: เรียนรู้หรือทำนายการซื้อสินค้า/หมวดจากอดีต แล้ว NestJS ใช้ผลเพื่อเลือก candidate quest ที่ผ่าน policy และมอบให้ผู้ใช้ เป้าหมาย แต้ม และ expiry ยังอยู่ภายใต้ backend ส่วน completion ยังยึดหนึ่ง paid order หลังส่วนลดและไม่หัก subsidy ตาม `FR-S06`

หากสร้างเควสย้อนหลังและดูว่าการซื้อที่ตามมาตรงเงื่อนไขหรือไม่ ต้องเรียกเป็นผลทดสอบย้อนหลังภายใต้เงื่อนไขสมมติ ไม่ใช่ผลของเควสที่ผู้ใช้ได้รับจริง ไม่สามารถวัดผลของแต้ม/ระยะเวลา/การมอบเควสต่อพฤติกรรมจากข้อมูลนี้โดยตรง

ข้อเสนอนี้ต้องปรับเป้าหมายและ features ในแผนเดิมที่เป็น `P(quest_completed)` หลังผู้ใช้อนุมัติ ไม่จำเป็นต้องเปลี่ยน CatBoost โดยอัตโนมัติ และยังไม่ได้เลือกเทคนิคหรือเพิ่มโมเดลใหม่จาก audit นี้

## 8. สิ่งที่ต้องตัดสินใจก่อนใช้เป็น dataset หลัก

1. เป้าหมายการเรียนรู้: เลือก/ทำนายความสนใจสินค้า หมวด หรือพฤติกรรมการซื้อในช่วงถัดไป แล้วเชื่อมผลกับ candidate quests อย่างไร
2. ระดับหมวดที่ใช้และ mapping ไปสินค้า/หมวดที่เว็บมีจริง ไม่ส่ง foreign product IDs ไปมอบเควสตรง ๆ
3. วิธีใช้ household/store source IDs เพื่อทดลอง โดยไม่อ้างว่าเป็นบุคคลหรือ merchant เดียวกับระบบเรา
4. ความหมายยอดเงิน ส่วนลด หน่วย และการตั้งเป้าหมายในสกุลเงินของโปรเจกต์
5. Cleaning ของ quantity ศูนย์, ยอดศูนย์, unknown metadata และหมวดที่อยู่นอกขอบเขต
