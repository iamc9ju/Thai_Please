# แบบร่าง: AI เสนอเควส 3 ข้อ และผู้ใช้เลือก 1 ข้อ

วันที่: 28 ตุลาคม 2026

สถานะ: เอกสารตั้งต้นจากการสนทนา ผู้ใช้สั่ง implementation แล้วในวันที่ 28 ตุลาคม 2026 ค่าเริ่มต้นและวิธี deploy ที่เลือกใช้จริงดู [คู่มือ v3](QUEST_PROPOSALS_RUNBOOK_TH.md) และหลักฐานการตรวจดู [ExecPlan](../../.agent/plans/quest-proposal-selection.md) ไม่มีการ apply migration กับข้อมูลแอปอัตโนมัติ รายการรอตัดสินใจด้านล่างเป็นประวัติประกอบการออกแบบ

## 1. ปัญหาและเหตุผล

บันทึกการตัดสินใจเมื่อ implementation: ใช้ค่าเริ่มต้นชุด24ชั่วโมง/พัก15นาที/สร้างสูงสุด3ชุดต่อวันไทย, รอบรับและอายุเควส7วันจากเลือกสำเร็จ, ประวัติเควส90วัน/latest10, มีบิลเงินส่วนตัวเป็นบวกขั้นต่ำ3บิล, duplicateใช้ประเภท+หมวด+ยอดและเว้น7วัน, ไม่มีbusiness spend ceiling มีเฉพาะDecimal storage limit ทุกค่าที่ปรับได้อยู่ในpolicy v3 ข้อความว่า “รอยืนยัน” ในส่วนการสนทนาด้านล่างเป็นประวัติ ไม่ใช่สถานะimplementationปัจจุบัน

การย้ายข้อมูลเลือกใช้การยกเลิกเฉพาะlegacy ACTIVEที่ไม่หมดอายุพร้อมaudit ไม่ล็อกรอบใหม่จากเควสที่ยกเลิก Workerใช้queueบนlogsและlease: queuedงานกลับมาทำได้หลังrestart แต่งานที่เริ่มproviderแล้วและขาดผลจะจบเป็นFAILEDเมื่อหมดlease ไม่replayproviderอัตโนมัติ

- ระบบเดิมสร้างตัวเลือกจากยอดเฉลี่ย ×1 และ ×1.5 แล้วให้ Gemini ให้คะแนนทุกตัวเลือก ทำให้เลือกยอดอื่นที่เหมาะกว่าไม่ได้
- บิลสูง เช่น ค่าใช้จ่ายจำเป็นบางครั้ง อาจดึงค่าเฉลี่ยขึ้น ขณะที่มัธยฐานอย่างเดียวก็ไม่อธิบายพฤติกรรมหลายกลุ่ม
- การเพิ่มสูตรตัวคูณ กลุ่มยอด และข้อยกเว้นเพื่อสร้างตัวเลือกให้ครอบคลุมทำให้ระบบซับซ้อน
- ยอดรวมที่นับเงินรัฐช่วยทำให้เมื่อสิทธิช่วยจ่ายหมด ผู้ใช้อาจต้องออกเงินเองมากขึ้นเพื่อผ่านเป้าหมายเดิม
- เพดาน 100 บาทเท่ากันทุกคนอาจไม่เหมาะกับพฤติกรรมที่แตกต่างกัน
- ข้อเสนอที่ผ่านกฎยังอาจไม่เหมาะกับผู้ใช้ การมีตัวเลือกช่วยให้ผู้ใช้เลือกตามบริบทของตน แต่ไม่รับประกันว่าจะมีข้อที่เหมาะเสมอ

## 2. ทิศทางที่ตกลง

1. เปลี่ยนจาก AI จัดอันดับชุดตัวเลือก เป็น AI เสนอเควสเป้าหมาย 3 ข้อ
2. Backend ตรวจข้อเสนอทั้งหมดก่อนแสดง ผู้ใช้เลือก 1 ข้อจึงเกิด assignment
3. ประเภทที่รองรับยังมี MIN_SPEND และ CATEGORY_SPEND ใช้ได้ทุกร้านที่เข้าร่วม ไม่ผูกชื่อสินค้า product ID หรือร้านเดียว
4. ใช้เงินส่วนตัวหลังหักส่วนลด ไม่รวมเงินรัฐช่วย ทั้งสรุปประวัติและตรวจผ่าน ต้องสำเร็จด้วยหนึ่ง PAID receipt
5. ไม่ใช้สูตรค่าเฉลี่ย ×1/×1.5 บังคับยอด และไม่ใช้เพดานตัวเลือกเดิม 4 ต่อประเภท/รวม 8
6. ยกเลิกเพดานยอด 100 บาท ไม่มีเพดานธุรกิจใหม่ที่ตกลงแทนในขณะนี้
7. เป้าหมายเป็นจำนวนบวกหน่วยละ 10 บาท เช่น 60, 90 หรือ 1,500 บาท ไม่รับยอดเศษจาก AI และไม่แก้ข้อเสนอเงียบ ๆ ด้วยการปัดหลังรับ
8. รางวัลคงที่ 20 พอยต์ ไม่แปรผันตรงกับยอดซื้อ อายุเควส 7 วัน Backend กำหนดพอยต์ อายุ และข้อความเอง
9. AI ไม่มีสิทธิ์ตัดสิน completion หรือเขียน wallet, point ledger หรือ reward โดยตรง

การไม่มีเพดานธุรกิจไม่ยกเลิกข้อจำกัดทางเทคนิค: ยอดต้องแทนค่าได้อย่างปลอดภัยตาม schema เงินของระบบ ใช้จำนวนเต็มหน่วยสตางค์หรือ decimal ที่แม่นยำ ห้ามใช้ floating point คำนวณเงิน

## 3. ข้อมูลส่งให้ AI

### ประวัติซื้อ

ใช้ rolling 30 วัน ณ asOf เดียวกัน ช่วง `[asOf - 30 วัน, asOf)` เฉพาะบิล PAID ของผู้ใช้ที่เกี่ยวข้อง

ชุดข้อมูลเริ่มต้นแบบกระชับ:

- จำนวนบิลทั้งหมด ค่าเฉลี่ย และมัธยฐานของเงินส่วนตัวต่อบิล
- การกระจายยอดเป็นช่วง พร้อมจำนวนบิล ไม่ใช้ค่าเฉลี่ยเพียงค่าเดียว
- แยกหมวดสินค้า: ID/ชื่อหมวด จำนวนบิลที่มีหมวดนั้น ค่าเฉลี่ยและมัธยฐานเงินส่วนตัวเฉพาะหมวดต่อบิลที่มีหมวดนั้น
- ระบุฐานเงิน ช่วงเวลา และเวอร์ชันวิธีสรุปอย่างชัดเจน

ยอดรวม ต่ำสุด/สูงสุด จำนวนบิล 7 วัน และวันซื้อหมวดล่าสุดเป็นข้อมูลเสริม ไม่จำเป็นต้องส่งทั้งหมดตั้งแต่เริ่ม ช่วงแบ่งการกระจายยอดต้องกำหนดผ่าน configuration และทดสอบก่อนใช้งาน

Backend จำแนกจาก order-item category snapshots ก่อนสรุป บิลเดียวมีหลายหมวดได้ จำนวนบิลรายหมวดรวมกันจึงอาจเกินจำนวนบิลทั้งหมด ห้ามนับยอดเงินส่วนตัวเต็มบิลซ้ำให้ทุกหมวด

ต้องกำหนดและทดสอบวิธีจัดสรรส่วนลดและเงินส่วนตัวลงรายการตามหลักการชำระเงินจริง โดยผลรวมต้องตรงกับยอดบิล และใช้วิธีเดียวกันสำหรับ summary และ completion

ไม่ส่งชื่อผู้ใช้ เลขบัตร เบอร์โทร token หรือข้อมูลส่วนตัวที่ไม่จำเป็น ไม่เดาหมวดจากชื่อร้าน ไม่ส่งรายละเอียดสุขภาพ หากมีข้อมูลประเภทดังกล่าวให้ทบทวนการใช้และลดรายละเอียดก่อน

การส่งข้อมูลดิบ 30 วันไม่ได้ถูกห้าม แต่เลือกใช้ข้อมูลสรุปเป็นหลักเพื่อลดข้อมูลและ token ต้องวัดคุณภาพจริงว่าสรุปเพียงพอหรือไม่

### ประวัติเควส

- สรุปผลสำเร็จและหมดอายุแยกประเภท หมวด และยอดเป้าหมาย
- รายการล่าสุดพร้อมผล เวลาเลือก/จบ และเวลาที่ใช้ทำสำเร็จ
- เควสที่กำลังทำ เพื่อป้องกันซ้ำ
- เวอร์ชันกฎและฐานเงิน แยกยอดรวมเดิมออกจากเงินส่วนตัวใหม่
- แยกการยกเลิกโดยระบบ ไม่ตีความเป็นความล้มเหลวของผู้ใช้

ข้อเสนอเบื้องต้น: สรุป 90 วัน และรายละเอียดล่าสุดไม่เกิน 10 รายการ ยังรอยืนยัน ค่าเหล่านี้ควรแก้ผ่าน validated config

### กฎและคำตอบ

ส่ง policy ที่อนุญาตและหมวดที่เลือกได้ให้ AI พร้อมข้อมูล โดย prompt และ Backend validator ใช้ policy รุ่นเดียวกัน

AI ตอบเฉพาะประเภท หมวดเมื่อจำเป็น และยอดเงินส่วนตัวเป้าหมายตาม strict schema ไม่เปิดให้เขียนข้อความเงื่อนไขอิสระ SQL หรือ executable expressions ต้องมีความแตกต่างของข้อเสนอที่ตรวจได้ รายละเอียดเกณฑ์ความแตกต่างยังต้องกำหนด

## 4. รอบการสร้าง การเลือก และรางวัล

แนวทางที่สนทนาไว้ (ค่าเริ่มต้นยังต้องยืนยันก่อน implementation):

- เมื่อเข้าหน้าเควส Backend ตรวจสถานะและสิทธิ์รอบก่อนเรียก AI
- มีเควส active ที่ยังใช้ได้ให้แสดงเควสเดิม มีชุดข้อเสนอที่ยังใช้ได้ให้ใช้ชุดเดิม ไม่เรียก AI ทุกครั้ง
- รับ 1 เควสต่อรอบ 7 วัน เริ่มรอบเมื่อเลือกสำเร็จ บันทึก selectedAt และ nextEligibleAt = selectedAt + 7 วัน
- ทำเสร็จก่อนเวลาก็ต้องรอ nextEligibleAt ไม่เริ่มนับ 7 วันใหม่จาก completion
- เลือกวันที่ 1 เวลา 10:00 ทำเสร็จวันที่ 2 ก็รับรอบใหม่ได้วันที่ 8 เวลา 10:00
- เมื่อหมดอายุและถึงสิทธิ์รอบใหม่จึงเริ่มรับชุดใหม่ได้
- การสร้างล้มเหลวไม่เริ่มรอบ ไม่หักสิทธิ์ และไม่ออกพอยต์
- เก็บเวลา UTC แสดงตามเวลาไทย ใช้ server clock เป็นผู้ตัดสินและตรวจ expiry แบบ exclusive

ข้อเสนอ: จองงบพอยต์และเริ่มอายุ assignment เมื่อเลือกสำเร็จ ตรวจสิทธิ์/งบซ้ำใน transaction เดียวกับ assignment ผู้ใช้เลือกได้เพียงหนึ่งข้อแม้กดพร้อมกันหลายอุปกรณ์

งานเรียก AI ที่ช้าควรมีสถานะ pending และดำเนินการผ่านกลไกงานที่ repository อนุมัติ ห้ามถือ database lock ขณะเรียก provider และห้ามใช้ GET อ่านหน้าเป็น mutation โดยไม่มี contract ที่ชัดเจน

## 5. การคัดทิ้งและการเติมข้อเสนอ

คัดทิ้งเมื่อ:

- ประเภทไม่รองรับ หรือหมวดไม่มี/ไม่ active/ไม่อยู่ใน allow-list
- ยอดไม่เป็นบวก ไม่เป็นหน่วยละ 10 บาท หรือเกินขอบเขตการแทนค่าที่ระบบรองรับ
- ผูกสินค้า ร้าน หรือรวมหลายบิล หรือเพิ่มเงื่อนไขนอก schema
- ซ้ำในชุด หรือผิดกฎเว้นซ้ำจากประวัติ
- ขาดข้อมูล ชนิดผิด หรือมี field นอก strict schema

ยอดสูงกว่าค่าเฉลี่ยไม่ใช่เหตุคัดทิ้งโดยอัตโนมัติหากไม่มีกฎนั้น ความถูกต้องตาม policy กับความเหมาะสมต้องประเมินแยกกัน

ผู้ใช้ยังไม่ถึงรอบ มี assignment active หรืองบไม่พอเป็นเงื่อนไข eligibility/assignment ไม่ใช่เหตุระบุว่า AI เสนอผิด

แนวทางเติมที่ผู้ใช้ยอมรับให้ใช้เป็นฐานการออกแบบ:

1. เรียกสร้าง 3 ข้อ ตรวจและเก็บข้อที่ผ่าน
2. ถ้าไม่ครบ ขอเติมเฉพาะที่ขาด พร้อมเหตุผล rejection แบบปลอดภัยและข้อที่มีแล้วเพื่อกันซ้ำ
3. ไม่เกิน 2 provider calls ต่อการสร้างชุด รวมการสร้างครั้งแรก การเติม และ retry ที่เรียก provider ใหม่ ห้ามซ้อน retry จนเกินขอบเขต
4. ได้ 3 ข้อแสดงตามปกติ ได้ 1–2 ข้อแสดงเท่าที่ผ่าน ได้ 0 ข้อแสดงสร้างไม่ได้และให้ลองภายหลัง
5. ต้องมีกฎพัก/จำกัดการลองใหม่และ budget ของการสร้าง แยกจากรอบรับรางวัล 7 วัน

## 6. ข้อมูลและขอบเขตการเปลี่ยน

- เก็บข้อเสนอรอเลือกแยกจาก assignment ที่มีสิทธิ์ตรวจ completion
- ใช้ quest_generation_logs สำหรับประวัติ generation ต่อ ไม่เพิ่ม quest_generation_runs ที่ซ้ำหน้าที่
- ตรวจ schema ปัจจุบันก่อนตัดสินใจว่าข้อเสนอและชุดข้อเสนอควรเก็บอย่างไร อาจต้อง migration แต่เอกสารนี้ไม่ได้กำหนดให้เพิ่มตารางใดล่วงหน้า
- เก็บ provider/model/prompt/policy/summary/rule versions, proposal validation results, การเลือก และเวลาที่จำเป็น เพื่ออธิบายย้อนหลัง
- API สร้าง/เลือกต้องตรวจ ownership, authorization, CSRF ตามรูปแบบ session, idempotency และ concurrency
- เปลี่ยน UI ให้มี pending, waiting-to-select, active, completed-waiting-next-round, expired, unavailable และ permission/error states
- วัด generation failure, invalid proposal, เลือกข้อใด, completion/expiry และต้นทุนพอยต์ ไม่ถือว่าพอยต์เท่ากันหมายถึงความยุติธรรมครบทุกด้าน

## 7. Requirements และความเข้ากันได้

เอกสารปัจจุบันที่เกี่ยวข้อง: [Requirements](../REQUIREMENTS.md), [Policy เดิม](QUEST_POLICY_TH.md), [Backend เดิม](QUEST_BACKEND_TH.md)

Traceability เบื้องต้น: FR-C07 (quest journey), FR-S01–FR-S06 ตามหัวข้อความสามารถใน requirements ปัจจุบัน ต้องตรวจ ID/ข้อความจริงอีกครั้งตอนทำแผน implementation ไม่อ้างเลขจาก AGENTS แทน requirements โดยอัตโนมัติ

มีการเปลี่ยนข้อกำหนดสำคัญสองเรื่อง:

1. จากมอบอัตโนมัติ/ไม่กดรับ เป็นเสนออัตโนมัติแล้วเลือกก่อนมอบ
2. จาก final spend หลังส่วนลด เป็น personal contribution หลังส่วนลดสำหรับ quest summary และ completion

ต้องแก้ requirements, invariant ที่เกี่ยวข้อง, contracts, policy versions และ tests ในการ implement จริง ไม่เปลี่ยน financial receipt facts เดิม

แนวทาง migration ที่เสนอ: ยกเลิกเฉพาะ assignment เก่าที่ยัง active และไม่หมดอายุซึ่งใช้ฐานเดิม พร้อมเหตุผลและเวลา เก็บ completed/expired, immutable receipts และพอยต์เดิม ไม่ re-evaluate หรือออกพอยต์ย้อนหลัง ต้องกำหนดผลต่อสิทธิ์รับรอบใหม่และการคืน reservation ก่อนรัน migration

## 8. เรื่องที่ยังต้องสรุปก่อนลงโค้ด

- ยืนยัน 1 assignment ต่อ 7 วันจากเวลาเลือก แทนกฎเดิมวันละ 1
- อายุชุดข้อเสนอ การข้าม/ขอชุดใหม่ และ rate limit/cooldown ของการสร้าง (ก่อนหน้านี้เคยเสนอวันละ 1 ชุด ยังไม่ใช่ข้อสรุป)
- ยืนยันช่วงประวัติเควส 90 วัน/10 รายการล่าสุด
- นิยามข้อเสนอที่แตกต่างกัน และ duplicate identity/cooldown ให้รองรับ 3 ข้อและประวัติเดิม
- พฤติกรรมกรณีประวัติซื้อ/เควสไม่มีหรือน้อย ต้องไม่แต่งประวัติหรืออ้างความสามารถจ่ายที่ไม่มีหลักฐาน
- วิธีจัดสรรเงินส่วนตัวรายรายการ วิธีสรุปการกระจายยอด และหมวดที่อนุญาต
- อายุพอยต์ งบรางวัลเดิม และข้อจำกัดทางเทคนิคของยอดต้องตรวจ compatibility ไม่สมมุติว่าถูกยกเลิกพร้อมเพดาน 100 บาท
- สถานะและสิทธิ์หลังยกเลิกเควสเก่าระหว่าง rollout

## 9. หลักฐานที่ต้องมีเมื่อ implement

- Unit: สถิติเงินส่วนตัว, mixed-category allocation/rounding, policy/schema, duplication, time boundaries และ empty history
- Provider: malformed/adversarial output, invalid categories/amounts, เกินจำนวน, เติมแล้วซ้ำ, 0/1/2/3 ข้อ และ call limit
- PostgreSQL integration: migration จากข้อมูลเดิม, เลือกพร้อมกัน/เลือกซ้ำ, ownership, reservation/budget, assignment และ point reward uniqueness
- Contract/UI: เลือกได้หนึ่งข้อ ชุดหมดอายุ งบเปลี่ยนหลังสร้าง รอบ 7 วันและสถานะรอ/ล้มเหลว
- Payment/completion: เงินรัฐอย่างเดียวไม่ทำให้ personal-spend quest ผ่าน, ส่วนลด/หมวดจัดสรรถูกต้อง, หนึ่ง receipt และ reward atomic/idempotent
- ตรวจ token/latency/validity ด้วยข้อมูลทดสอบ ไม่สมมุติว่า AI สร้างหรือเลือกประหยัดกว่าจนกว่าจะวัด

เอกสารนี้เสร็จในฐานะบันทึกการออกแบบ ไม่ใช่การประกาศว่าฟีเจอร์ implement หรือผ่าน tests แล้ว
